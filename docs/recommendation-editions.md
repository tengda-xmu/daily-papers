# 推荐批次、热度与自动精读

每天北京时间 21:00 起更新，保留现有补偿检查。手动更新生成当天下一批；首页展示最新批次，历史归档按日期展开。暂无可新增推荐时只登记检查结果，不生成空批次。

新论文可先推荐，再由本机助手自动完成摘要级中文精读。扩展阅读不重复出现在扩展阅读中；完成精读并通过研究方向、方法价值与证据评估后，可以升级为核心推荐。核心旧文可在距上次核心推荐至少 30 天、出现新的明显升温证据且通过质量评估后再次推荐。两类旧文每批合计最多一篇；个人星级不参与推荐。

## 热度依据

阈值集中在 `config/recommendation-policy.json`，属于产品默认值，不是统一学术评价标准。

- 被引：近 30 天、上次核心推荐之后，同源至少 3 个采样日期、跨度至少 14 天，至少两个区间增长，无下降，增加至少 5 次且不少于起点的 20%；零起点只检查增量。最新观察不超过 3 天。
- 学术关注：同一时间范围内，至少两家独立来源在不同日期实质介绍该论文；明确论文 DOI、可核实链接和有效内容才能关联。转载同一报道去重，普通会议通知和公开搜索片段不计入。
- 两者任一满足即可进入候选，不保证入选。来源分别保存，缺失不算零、采样失败不伪造增长；计数下降后重新积累比较基线。历史数据不足时等待观察。

## 数据与发布

`data/editions/index.json` 索引所有已发布批次，快照位于 `data/editions/日期/批次标识.json`；GitHub 运行 ID 是幂等批次标识。`data/archive/日期.json` 保持当天最新批次兼容入口。名单、顺序、决策依据固定；精读可以单独补充。

`data/updates/运行ID.json` 记录更新结果，`data/recommendation-heat.json` 保存带来源和日期的观察。每日工作流部署成功后才提交数据；下次运行先核对公开批次索引，恢复部署成功但提交失败的记录。精读部署与日报使用同一个工作流并发组。

旧数据迁移：`python -m tools.recommendation_data --recover`。首次迁移在 `.local/recommendations-before-editions-*` 备份原归档，并扫描已有日期归档、Git 历史和本机更新历史；重复执行不新增批次，不编造缺失快照。公共恢复使用 `--reconcile`。

## 本机精读

助手启动后及运行期间自动同步公开批次，按最新核心、最新扩展、历史待完成的顺序处理，用户对话优先。任务存于 `.local/codex-bridge/reading-queue.sqlite3`，与个人对话数据库分离。先复用对应论文的原文 PDF，再查询出版社、开放全文及元数据来源。全文分批读取，保存页码或段落标识；扫描页及无法识读的 PDF 公式、图表通过原页图片补读。未覆盖全部正文时不会标为全文完成。

只有可靠完整摘要时先发布摘要解读，随后继续每天尝试补充全文。缺资料采用缓存与退避，新原文到达后重新排队；模型生成最多自动尝试三次，可手动重试。分批检查点在重启后保留，发布失败独立重试，不重新生成。页面区分资料获取中、摘要解读已完成且全文待补充、全文精读已完成，以及暂时无法获取资料。

有效结果经过固定字段白名单校验，发布到 `connector-data` 的 `data/auto-reading/`，必要状态存于 `data/reading-status/`，触发网站重新构建；不运行推荐筛选、不改变批次编号。只有核对公开结果后才显示已发布。可复用用户已保存的对应原文 PDF，但原 PDF、私人批注、星级、聊天和授权均不进入公开数据。升级前自动备份旧精读队列，保留旧解读并补充全文任务。

设置中的“自动中文精读”可查看进度和重试。接口沿用配对授权：

- `GET /api/recommendations/reading-tasks`
- `POST /api/recommendations/reading-tasks/{paper_id}/retry`
- `GET /api/recommendations/update` 返回批次、精读及热度采集状态。

手机公开浏览不调用本机任务接口，也不要求配对。
